# Deployment (Render)

One web service serves the API and the website from the same address, plus one Postgres database. Defined in `render.yaml` at the repository root.

## Why one address
The website and API share an origin, so there are no cross-site cookie settings, no CORS, and the sign-in cookies (`es_shop`, `es_studio`, `es_admin`, ...) are first-party. A custom domain goes straight onto the Render service (no proxy in front, which keeps TLS, client addresses and rate limits simple).

## First deploy
1. Render dashboard: **New > Blueprint**, choose this repository. Render creates `eazystores-db` and `eazystores`.
2. Fill the values it asks for (`sync: false` in the blueprint):
   | Variable | Value |
   |---|---|
   | `PUBLIC_URL` | `https://www.eazystores.ca` (or the Render address until the domain is attached) |
   | `ALLOWED_ORIGINS` | the same address, https only; add the apex too if both are used |
   | `SMTP_URL`, `EMAIL_FROM` | from the email provider (see Email below) |
   | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` | `npm run make-vapid -w @eazystores/api` on any machine; keep the private key secret |
   `AD_SECRET` and `NOTIFY_SECRET` are generated by Render. Do not rotate `NOTIFY_SECRET` casually: every unsubscribe link already emailed stops working.
3. The first deploy runs `npm run migrate` before the new version starts (forward-only, then the launch categories). It never seeds demo data, and the demo seed refuses to run when `NODE_ENV=production`.
4. If a value is missing or unsafe the service stops at start-up and the log lists every problem (`prod-check.ts`). Fix and redeploy.
5. Create the first administrator from the service's Shell tab: `npm run make-staff -w @eazystores/api -- you@yourdomain.ca admin 'a long password'`. Then create other staff from the admin console. (There is no `ADMIN_EMAILS` variable: staff are created deliberately, never by environment.)
6. Check `https://<address>/readyz` returns 200 and the home page loads.

## Settings that matter
- `NODE_ENV=production`: secure cookies, the production checks, no mock payments, no fake clock.
- `TRUST_PROXY=true`: required behind Render's load balancer so sign-in rate limits and ad click checks see the real visitor address.
- `UPLOAD_DIR=/var/data/uploads` on the persistent disk. **A disk limits the service to one instance and means a short pause on each deploy.** To scale out later, move media to object storage first (not built).
- Tuning (defaults are fine to start): `DB_POOL_MAX` 20, `DB_STATEMENT_TIMEOUT_MS` 30000, `DB_LOCK_TIMEOUT_MS` 15000, `DB_IDLE_TX_TIMEOUT_MS` 30000, `LIST_CACHE_MS` 10000. Keep the database plan's connection limit above `DB_POOL_MAX` (plus a few for migrations and the Shell).
- `PAYMENT_PROVIDER` is intentionally unset. With no provider checkout answers "payments not configured". Setting it to `mock` is refused at start-up.

## Custom domain plan (`eazystores.ca` is a placeholder)
1. Buy the domain; keep DNS with the registrar or Cloudflare (DNS only, **grey cloud / no proxy**, so Render terminates TLS).
2. Render service > Settings > Custom Domains: add `www.eazystores.ca` and `eazystores.ca`. Render shows the DNS records to create: a `CNAME` for `www` to the service address, and for the apex either an `ALIAS/ANAME` to it or the A record Render lists. Render redirects the apex to `www` and issues the TLS certificate itself.
3. Wait for both to show Verified, then set `PUBLIC_URL` and `ALLOWED_ORIGINS` to `https://www.eazystores.ca` and redeploy.
4. Check: `curl -I https://www.eazystores.ca` shows `strict-transport-security` and the page policy; a sign-in sets a `Secure` cookie.

## Email DNS (needed before real mail arrives in inboxes)
At the email provider: verify the domain, then add the **SPF** include, the **DKIM** records they give you, and a **DMARC** record (start with `v=DMARC1; p=none; rua=mailto:dmarc@eazystores.ca`, move to `quarantine` after a few clean weeks). Send a test from the studio "send me a test" and check headers show `spf=pass dkim=pass dmarc=pass`.

## Releasing
Merge to `main` after the checks in `docs/OPERATIONS.md` pass, then press **Manual Deploy** in Render. A failed migration or failed health check leaves the previous version running. Migrations are forward-only: to undo a release, ship a new migration or restore a backup (`docs/BACKUP_RECOVERY.md`).
